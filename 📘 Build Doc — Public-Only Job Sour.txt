2) URL Planner (prebuild all scenarios before fetching)
Why: To avoid “loss” and ensure coverage, we generate a deterministic list of URLs across (keyword × location × recency × page) for each source. The fetchers simply iterate this list and extract results.
2.1 Naukri URL pattern (public)
https://www.naukri.com/<slug>-jobs?k=<keyword>&l=<location>&sort=date&pageNo=<page>


<slug>: keyword with spaces → hyphens.
sort=date: newest first.
Pagination: pageNo=1..MAX_PAGES_NAUKRI.

2.2 Indeed India URL pattern (public)
https://in.indeed.com/jobs?q=<keyword>&l=<location>&fromage=<days>&sort=date&start=<offset>


fromage=<days>: jobs posted within X days (1, 3, 7).
sort=date: newest first.
Pagination via start=<offset> (0, 10, 20 … often 10 per page; some regions 15).


Remote/hybrid note: Indeed’s explicit remote filter parameters vary and are not always honored anonymously. We still detect work mode by scanning job card text for “Remote/Hybrid/WFH”.

2.3 Hirist URL pattern (public)
https://www.hirist.com/search/?query=<keyword>&location=<location>&page=<page>


Many Hirist pages expose query by query & location.
Some sites also support remote=1. Since this can vary, we prefer detecting remote/hybrid from text rather than relying on a parameter.
Pagination: page=1..MAX_PAGES_HIRIST.


Important: Exact parameter names may evolve. This planner uses common, widely seen patterns. If a parameter stops working, the agent should keep the query minimal (query+location) and rely on content scanning. This keeps dependencies low and resilience high.


3) Connectors (Extraction logic per source)
All connectors:

Use a shared requests.Session with a desktop user agent.
Timeout = 20s.
Random delay (1.5–2.5s) between page requests.
Never require login.

3.1 Naukri (HTML, public)
Selectors (as observed commonly):

Card: div.jobTuple
Title: a.title
Company: a.companyName or span.company
Location: span.place
Posted: span.jobTuple-job-posted (parse “X days ago”, “today”)
Link: from a.title[href]

3.2 Indeed India (HTML, public)
Selectors (modern Indeed SERP):

Card: div.job_seen_beacon (common) or a.tapItem (fallback anchor for job card)
Title: inside h2.jobTitle or anchor text
Company: span.companyName
Location: div.companyLocation
Posted: span.date or text containing “Just posted”, “Today”, “X days ago”
Link: a.tapItem[href] (relative; prepend https://in.indeed.com)


Indeed markup changes more often; we implement fallback selectors and text heuristics to reduce fragility.

3.3 Hirist (HTML, public)
Selectors (typical tech job boards):

Card: .job-card or .job (we’ll try both)
Title: a.job-title or h3 inside the card
Company: .company or .company-name
Location: .location
Posted: .posted-date or .posted (parse similar to Naukri)
Link: title anchor href


If no selectors match, we scan anchors within the results container for typical job link patterns and extract text heuristically.

3.4 ATS JSON (optional; public)

Greenhouse: GET https://boards-api.greenhouse.io/v1/boards/<shortname>/jobs

Fields: title, absolute_url, location.name, updated_at[:10]


Lever: GET https://api.lever.co/v0/postings/<company>?mode=json

Fields: text, hostedUrl, categories.location, createdAt (ms epoch → date)




4) Deduplication (Clear logic)
We deduplicate across all sources to avoid duplicates in your final CSV/JSON.
4.1 Canonical key (strict)
key = sha1( lower(company) + '|' +
            lower(title)   + '|' +
            lower(location or '') + '|' +
            absolute_link ).hex[:16]


This collapses exact same job across sources (same title/company/location + same URL or canonicalized version).
We prefer absolute link (e.g., Indeed link normalized with full domain).

4.2 Fuzzy guard (optional, advanced)
For the basic version, we do not do fuzzy dedup. If you later want to merge near‑duplicates (e.g., DLP Engineer vs DLP/CASB Engineer), you can add:

Title normalization (remove slashes, punctuation).
Jaro‑Winkler / Levenshtein (requires extra dependency).
Company normalization (strip India Pvt Ltd, etc.).

Decision: Keep strict key now (no extra deps, deterministic), expand later if needed.

5) Relevance Scoring (basic)

Start at 0.0; clamp to 1.5.
Recency (based on parsed date):

≤ 1 day: +1.0
≤ 7 days: +0.7
≤ 30 days: +0.4


Keyword matches: +0.1 × count(KEYWORDS seen in title/location)


(Optional later) Work mode bonus if text contains Remote/Hybrid/WFH: +0.2.

7) Orchestration (execution order)

Generate URL list for Naukri, Indeed, Hirist:

Each combination: (keyword × location × recency × page)


Iterate URLs source‑by‑source:

Naukri (HTML)
Indeed (HTML)
Hirist (HTML)


Optionally fetch ATS JSON if configured.
Normalize → Dedup → Score.
Write outputs (JSON + CSV) once at the end.


Politeness: Sleep 1.5–2.5s between page fetches; stop early when a page returns no cards.

## 1) URL Planner & Coverage

**Issue: Combinatorial URL explosion**

*   `keyword × location × recency × pages` grows fast; many URLs return near‑duplicates or empty pages.

**Impact:** Wasted requests → higher block risk, slower runs, more duplicates.

**Fix (minimal deps):**

*   **Adaptive paging** per query: stop after **2 empty/low-yield pages** in a row.
*   **De‑duplicate planned URLs** before fetch.
*   **Prioritize** high‑yield queries first (e.g., security terms; India + Tier‑1 cities).
*   **Throttle recency**: use `[3, 7]` instead of `[1,3,7]` until needed.

**Snippet (adaptive stop):**

```python
def run_query_with_adaptive_paging(plan_urls, fetch_fn, max_empty=2):
    all_rows = []; empty_streak = 0
    for url in plan_urls:
        rows = fetch_fn(url)
        if not rows:
            empty_streak += 1
            if empty_streak >= max_empty:
                break
        else:
            empty_streak = 0
            all_rows.extend(rows)
        sleep_a_bit()
    return all_rows
```

## 3) Rate‑limits, 429 & Captcha

**Issue:** No special handling for **HTTP 429 (Too Many Requests)**, **403**, or **Retry‑After** header.

**Impact:** You get throttled → partial results → opaque failures.

**Fix:**

*   On **429**: parse `Retry‑After` (seconds), sleep that long + jitter, retry once.
*   On **403/CAPTCHA**: back off longer and **skip that source** for the rest of the run.
*   Add **Accept / Accept‑Language** headers to look more like a real browser.

**Snippet (basic retry):**

```python
def get_with_backoff(url, session, timeout=20, max_retries=2):
    for attempt in range(max_retries+1):
        r = session.get(url, timeout=timeout)
        if r.status_code == 429:
            ra = int(r.headers.get("Retry-After", "5"))
            time.sleep(ra + random.uniform(1,3))
            continue
        if r.status_code in (200, 404):
            return r
        if r.status_code == 403:
            logging.warning("403 for %s; backing off", url)
            time.sleep(10 + random.uniform(1,3))
            return r
        time.sleep(2 + attempt)
    return r
```

REMOTE_PHRASES = [r"\bremote\b", r"work\s*from\s*home", r"\bwfh\b"]

8) Troubleshooting


0 results from a source

Reduce combinations: use fewer keywords or locations
Increase recency_days (e.g., use [7, 14])
Update selectors (sites change HTML often)



429/403 frequently

Increase request_delay_range, reduce max_pages
Ensure you don’t hit job detail pages; only list pages



Duplicates slipping through

Add more aggressive canonicalization per source (e.g., unify Naukri IDs if present)



Wrong work mode

Expand phrase lists and negatives in infer_work_mode()



You need only “delta”

Keep the default incremental mode (uses seen_ids.json) and consume current run output only
